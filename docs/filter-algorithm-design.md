# 筛选核心算法设计（正确性 × 全面性）· Filter Algorithm v1

> 版本：2026-10-29 · 状态：设计稿，确认后随 M2 实施。
> 两大核心算法分工：**筛选算法（本文）决定一条搜索结果「是否该进入职位池、进哪个区、信多少」；排序算法（v2，下一份设计）决定池内「谁排前面」。** 筛选宁可保守放行，排序负责精排——过度筛选造成的漏检（假阴性）比多看几条疑似结果（假阳性）代价高得多。

## 0. 设计原则

1. **不静默丢弃**：任何被拦截的结果都进「隔离区」并给出机器可读原因，用户可查看、可申诉（一键恢复）；杜绝黑箱删除。
2. **三区而非二值**：结果不是「收/拒」，而是 `accepted（可投递）/ unverified（待核实）/ quarantined（隔离）`，配合状态门控形成完整处置矩阵。
3. **灰区保留**：相关性处于灰色地带的结果一律保留并标记，交给排序降权处理；筛选的召回底线由阈值下限保护。
4. **可解释可复现**：每条记录带 `filter_trace`（各阶段判定+得分+原因），导出报告可复现当时判定。
5. **阈值可调**：宽松/标准/严格三档预设 + 高级页逐项可调；默认「标准」。
6. **漏斗可观测**：六阶段通过率全部落库，异常低通过率触发告警（说明查询解析或提取器坏了，而不是真的没有职位）。

## 1. 六阶段流水线总览

```text
原始发现结果（SERP 摘要 / 抓取解析记录）
   │
   ▼ S0 查询意图与预过滤   —— 意图解析错误 = 全错，先保证「找的是对的东西」
   ▼ S1 结构与字段校验     —— 数据本身合法（薪资区间/日期/枚举/必填）
   ▼ S2 语义相关性判定     —— 这条结果是不是用户问的岗位（三档分流）
   ▼ S3 实体消歧          —— 「这家公司」到底是谁，置信度多少
   ▼ S4 时效与状态门控    —— active/unverified/expired/closed 判定
   ▼ S5 去重合并与置信度   —— 复用 M1 dedup，多源一致性加分，产出综合置信度 C
   │
   ▼
三区处置 + filter_trace 入库 → 交给排序算法
```

每阶段只做一件事、只打一个分，失败原因独立记录；任何阶段都不因「数据缺失」而拒绝（缺失走标记，见 S1）。

## 2. S0 查询意图与预过滤

**意图解析**（漏斗的最上游，决定后续所有匹配）：

```python
Intent = {
  role_terms:   ["后端", "工程师"],      # 岗位词组（同义词库展开：后端↔服务端↔backend）
  city:         "成都",                  # 城市词（含「成都市」归一）
  category:     "互联网/软件",           # 可选，映射到 11 类别枚举
  exclude_terms: ["外包"],               # 显式排除词（用户输入 -外包）
  salary_hint:  (15, 25),               # 可选，从查询词提取的期望
}
```

同义词库 `backend/filters/synonyms.yaml`（数据文件，用户可编辑）：岗位词组、城市别名（蓉城→成都）、类别映射。解析失败的词落入 `unmatched` 并回显给用户确认，不猜。

**SERP 预过滤**（fetch 前省预算）：域名不在站点注册表 ∧ 域名与查询无词面关联 → 仅存摘要不抓取；标题命中 spam 特征（「日结/加微信/点击申请」高密度）→ 直接隔离 `spam_suspect`。

## 3. S1 结构与字段校验

| 规则 | 处置 |
|---|---|
| 必填缺失（职位名/公司名/来源 URL 任一为空） | 隔离 `missing_required` |
| 薪资 min>max、负数、>500K/月 | 该字段作废记 `salary_invalid`，**记录保留**（薪资缺失≠作废） |
| 日期无法解析 / 发布日期在未来 | 作废该字段记 `date_invalid`，记录保留；未来日期视为抓取噪声 |
| 城市/区县不在行政区划表 | 记 `geo_unverified`，保留 |
| 经验/学历不在枚举 | 原文保留 + 归一失败标记 |

**原则：字段级错误销毁字段，记录级错误才销毁记录。** 缺失与非法字段进 `missing_fields`，排序时取中性分（沿用 M1 哲学）。

## 4. S2 语义相关性判定（三档）

```
rel(query, record) = 0.45·title_hit + 0.20·body_hit + 0.20·city_match + 0.15·category_match
```

- `title_hit`：岗位词组命中度。短语命中=1.0；全部词素命中=0.8；部分命中=命中比例×0.6；标题全靠同义词库命中 ×0.9 折扣；
- `body_hit`：摘要/正文命中比例（截尾到 [0,1]）；
- `city_match`：精确=1.0；同城周边/省份=0.5；不符=0；无城市字段=0.5（中性，不惩罚缺失）；
- `category_match`：类别词命中=1.0，未声明类别=0.5（中性）。

**分档**（标准档阈值，可调）：

| rel | 处置 | 含义 |
|---|---|---|
| ≥ 0.55 | `accepted` | 进入榜单 |
| 0.30 – 0.55 | `accepted_suspect` | 进入榜单但挂「疑似相关」标记，排序降权（-10% 综合分） |
| < 0.30 | `quarantined` | 隔离区，原因 `low_relevance`，可人工恢复 |

排除词命中（`exclude_terms` 出现在标题或正文）→ 直接隔离，原因 `user_excluded`。

## 5. S3 实体消歧（公司是谁）

匹配优先级与置信度：

| 证据 | entity_conf |
|---|---|
| 统一社会信用代码（USCC）一致 | 1.00 |
| 注册全称 + 注册地区一致 | 0.90 |
| 注册全称一致 | 0.75 |
| 规范化简称/显示名一致（去括号地名、去「有限公司」等后缀） | 0.60 |
| 仅显示名相似（≥0.85） | 0.50 |

- `entity_conf ≥ 0.75`：正常关联，公司级信号（口碑/法律）挂载；
- `0.50 – 0.75`：关联但挂「主体待确认」，**公司级口碑/法律信号不挂载**（防同名公司误伤）；
- `< 0.50`：不关联，该记录的 organization 显示原名+「未关联主体」。
- 一次搜索中同一规范化名对应 ≥2 个不同 USCC/注册地 → 全部降级为待确认并在 UI 提示歧义。

## 6. S4 时效与状态门控

判定规则（按优先级，全部留痕）：

| 证据 | 状态 |
|---|---|
| `validThrough < 今天`（JSON-LD）或页面明示「已截止/已招满/停止招聘」 | `expired` / `closed` |
| 发布 > 90 天 且 最近核查 > 30 天 且 无任何再确认证据 | `unverified`（`stale`） |
| 仅索引摘要可见、原文未核查 | `unverified`（`snippet_only`） |
| 抓取到原文且无负面时效证据 且 发布 ≤ 90 天 | `active` |

**红线（沿用主方案）**：`page_accessible ≠ actively_hiring`；页面标题写着在招只证明「发布时在招」，`active` 仍需 ≤90 天发布窗口约束。状态随每次核查更新，历史快照保留。

## 7. S5 去重、多源一致性与综合置信度 C

去重复用 M1（规范 URL 强合并 / 同公司+相似职位疑似合并），此处新增**多源一致性**：

```text
C = 0.30·source_trust      # 源类型可信度表（官网1.0 政务0.95 平台公开0.70 聚合0.55 导入0.40 索引摘要0.35）
  + 0.20·extraction_tier   # 提取层级：JSON-LD 1.0 > 站点解析 0.85 > Trafilatura 0.60 > 仅摘要 0.40
  + 0.20·field_completeness# M1 证据完整度归一
  + 0.15·entity_conf       # S3 结果
  + 0.15·consistency       # 多源一致：≥2 源字段一致 1.0；单源 0.5；字段冲突 0.2 + conflict 标记
```

C 只描述「信息可靠程度」，**不是**「公司在招」「公司好」的认证（展示文案约束同主方案 5.1 的 R 维度）。

**处置矩阵（状态 × 相关性 × C）**：

| | rel ≥ 0.55 | 0.30–0.55 | < 0.30 |
|---|---|---|---|
| active / unverified | **榜单区**（C≥0.7 正常；C<0.7 挂「建议人工核实」） | 榜单区+疑似相关 | 隔离区 |
| expired / closed | 归档区（默认隐藏，可切换查看） | 归档区 | 隔离区 |
| spam_suspect / user_excluded / missing_required | 隔离区 | 隔离区 | 隔离区 |

## 8. 全面性工程：怎么知道「找全了」

筛选算法的另一半职责是**保召回**，四个机制：

### 8.1 饱和度检测与早停（省预算不伤覆盖）
每个引擎×查询批次结束后计算**边际新增率** = 本批唯一新职位数 / 本批总数。连续 2 批 < 5% → 跳过剩余低优先级查询（按查询矩阵优先级），被跳过的查询在任务报告里如实列出 `skipped_by_saturation`。

### 8.2 覆盖率估计（Lincoln-Petersen 式）
对两引擎结果集 A、B：`N̂ ≈ |A|·|B| / max(1,|A∩B|)`，`估计覆盖率 = 观测唯一数 / N̂`。报告显示「估计已覆盖 ~78% 的可发现职位」，覆盖率异常低（<50%）时提示「建议更换引擎组合或增加查询词」。

### 8.3 漏斗健康监控
六阶段通过率落库（`search_tasks.funnel_json`）。告警规则：S2 通过率 < 20%（大概率意图解析或提取器故障）、S5 一致性冲突率 > 40%（疑似解析错位）。**把「没搜到」区分为「外部真没有」vs「我们筛错了」。**

### 8.4 召回保护底线
- 阈值下限保护：严格档也不允许 rel 门槛 > 0.70、城市匹配权重 > 0.25（防止用户调成「筛到没东西」）；
- 隔离区永久可恢复 + 恢复操作进入反馈回路（见 §10）。

## 9. 输出契约（filter_trace）

```jsonc
{
  "filter_version": "1.0.0",
  "zone": "accepted | accepted_suspect | quarantined",
  "status": "active | unverified | expired | closed",
  "confidence": 0.82,               // 综合置信度 C
  "relevance": 0.71,                // S2 得分
  "entity_conf": 0.9,
  "consistency": 1.0,
  "flags": ["snippet_only"],        // stale / snippet_only / conflict / salary_invalid …
  "stages": [ {"stage": "S2", "pass": true, "score": 0.71, "reason": ""}, ... ],
  "rejection_reason": null           // 隔离区必填：low_relevance/spam_suspect/user_excluded/missing_required
}
```

入库：`jobs` 增加 `filter_zone / confidence / rejection_reason / filter_trace_json`；榜单默认查询 `filter_zone IN (accepted, accepted_suspect) AND status NOT IN (expired, closed)`。排序 v2 消费：`confidence` 进入 R 维度证据、`flags` 影响展示、疑似相关降权 10%。

## 10. 评估与反馈回路

- **金标集**：`tests/golden/` 维护 ≥200 条标注样本（真实 SERP 结果人工标 rel 真值 + 虚构边界样本），CI 跑筛选回归：精度（隔离区里真垃圾比例）、召回（相关结果进榜单比例 ≥98% 目标）、各阶段通过率漂移 <10%；
- **用户反馈**：隔离区「这条其实相关」/ 榜单「这条无关」按钮 → 写入 `feedback` 表，按月汇总提示阈值调优建议（不自动改阈值，人工确认后改默认值）；
- **对抗样本**：日期异常、未来发布、超界薪资、同名公司、冲突薪资（两源 salary 不同）必须有用例。

## 11. 默认参数与决策点

| 参数 | 宽松 | 标准 | 严格 |
|---|---|---|---|
| rel 接受阈值 | 0.45 | 0.55 | 0.65 |
| rel 隔离阈值 | 0.20 | 0.30 | 0.40 |
| C「建议人工核实」线 | 0.55 | 0.70 | 0.80 |
| 饱和早停边际率 | 3% | 5% | 8% |
| 城市匹配权重上限 | 0.25（三档共同下限保护） | | |

| # | 决策点 | 推荐 |
|---|---|---|
| F1 | 疑似相关降权幅度 | 综合分 ×0.9（可调） |
| F2 | expired 归档区默认 | 默认隐藏、顶部开关一键查看 |
| F3 | 隔离区保留期 | 永久（随数据清理策略整体删除） |
| F4 | 覆盖率估计是否进导出报告 | 进（HTML 报告「覆盖与局限」章节） |

## 12. 实现落点与验收

| 模块 | 内容 |
|---|---|
| `backend/filters/intent.py` | 意图解析 + 同义词库加载 |
| `backend/filters/validator.py` | S1 字段校验 |
| `backend/filters/relevance.py` | S2 相关性 |
| `backend/filters/entity.py` | S3 消歧（消费 organizations.uscc） |
| `backend/filters/freshness.py` | S4 状态门控 |
| `backend/filters/confidence.py` | S5 一致性 + C |
| `backend/filters/funnel.py` | 漏斗统计、饱和早停、覆盖估计 |

**验收标准**：金标集召回 ≥98%、精度 ≥90%；漏斗各阶段通过率在 UI 任务详情可见；隔离区每条带机器可读原因且可恢复；断网重放历史结果判定不变（确定性）；同一结果重复过滤不产生重复记录。
